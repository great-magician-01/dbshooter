# DBShooter — 需求分析与技术选型

> 版本：v0.1（评审稿） · 2026-09-15

## 1. 需求理解

做一个 **Web 版的数据库管理工具**（对标 DBeaver 的核心体验），第一期功能：

| # | 功能 | 说明 |
|---|------|------|
| 1 | 多数据库连接管理 | 连接的增删改查、测试连接、连接树浏览元数据（库/表/视图/字段/索引） |
| 2 | 多 Tab SQL 工作台 | 左侧连接树 + 右侧多 Tab 页，每个 Tab = SQL 编辑器 + 执行结果网格，布局参考 DBeaver；**页签与 SQL 内容持久化到 sqlite，重开自动恢复** |
| 3 | 五类数据库支持 | SQLite、MySQL、PostgreSQL、Redis、MongoDB（第一批），架构上可插拔扩展后续数据库 |
| 4 | Text-to-SQL AI | 自然语言生成 SQL，结合当前连接的 schema 上下文，生成结果可插入编辑器/直接执行 |

### 1.1 关键差异点（设计前必须想清楚的事）

这五类数据库其实是 **三种操作模型**，UI 和后端抽象都要围绕这个现实设计：

| 模型 | 数据库 | 编辑器形态 | 结果形态 | 元数据树 |
|------|--------|-----------|---------|---------|
| SQL 模型 | SQLite / MySQL / PG | SQL 编辑器（高亮/补全） | 行列网格 / 影响行数 | 库 → Schema → 表/视图 → 字段 |
| 文档模型 | MongoDB | JSON 查询编辑器（`db.coll.find({...})`） | 文档列表（JSON 树/表格切换） | 库 → 集合 → 字段(采样推断)/索引 |
| 键值模型 | Redis | 命令行式编辑器（`GET`/`HGETALL`…） | 按 key 类型展示（string/hash/list/set/zset） | db0~15 → key 空间（按 `:` 分隔虚拟分组） |

结论：
- **后端要做"统一驱动接口 + 三种执行语义"**，而不是强行把所有数据库伪装成 SQL。
- **前端 Tab 有三种内容类型**：SQL 工作台、Mongo 查询页、Redis 键浏览器。
- Text-to-SQL 第一期只覆盖 SQL 类数据库；Mongo 的 text-to-MQL 留接口，Redis 不做。

### 1.2 第一期非目标（明确排除，避免范围蔓延）

- 多用户/权限体系（第一期定位：本地或内网单人使用，可选 access token）
- 数据可视化图表、ER 图、数据迁移/同步
- SQL 审核、慢查询分析等平台化能力
- 移动端适配

## 2. 技术选型

### 2.1 后端：Python vs Go —— **推荐 Python (FastAPI)**

| 维度 | Python + FastAPI | Go | 结论 |
|------|------------------|-----|------|
| SQLite 驱动 | `sqlite3` 标准库内置，零依赖 | `mattn/go-sqlite3` 需 CGO（Windows 需 MinGW，交叉编译麻烦）；`modernc.org/sqlite` 纯 Go 但小众 | **Python 胜** |
| MySQL / PG / Redis / Mongo 驱动 | asyncpg、PyMySQL、redis-py、pymongo，全部官方/社区一线 | pgx、go-sql-driver、go-redis、mongo-driver 同样成熟 | 平手 |
| 异构结果集处理 | 动态类型天然契合「columns + rows → JSON」 | 静态类型需大量 `interface{}`/反射，代码啰嗦 | **Python 胜** |
| AI / Text-to-SQL | OpenAI / Anthropic SDK、流式输出、结构化输出生态最成熟；prompt 组装/schema 序列化方便 | 调 LLM API 本质也是 HTTP，可以做，但生态和迭代速度弱 | **Python 胜** |
| 开发迭代速度 | 快，pydantic 模型即文档，FastAPI 自动生成 OpenAPI | 相对慢 | **Python 胜** |
| 部署分发 | 需要 Python 运行时（Docker 或 PyInstaller 打包缓解） | **单二进制 + 内嵌前端静态文件，分发体验最好** | Go 胜 |
| 性能/并发 | asyncio 足够（瓶颈在数据库 I/O，不在自身） | 更好，但此类工具用不满 | 平手（对本场景） |

**决策：Python 3.11+ / FastAPI / Uvicorn**。核心理由：这类工具的复杂度集中在「五种驱动的差异抹平」和「AI 能力迭代」上，Python 在这两点的开发效率优势明显；部署短板用 Docker 镜像（前端构建产物内嵌进镜像，单容器交付）解决。

后端关键依赖：

```
fastapi, uvicorn[standard]     # Web 框架（REST + WebSocket）
aiosqlite                      # SQLite 异步
asyncpg                        # PostgreSQL
aiomysql                       # MySQL
redis                          # Redis (redis-py 异步)
pymongo / motor                # MongoDB
pydantic v2                    # 数据模型
cryptography                   # 连接凭据加密存储(Fernet)
httpx                          # 调 LLM API（或官方 SDK）
```

> 注意：**不引入 SQLAlchemy/ORM**。数据库管理工具需要多语句执行、原生 introspection、数据库专有特性，ORM 只会碍事。直接用各驱动 + 自研薄抽象层。

### 2.2 前端：Vue 3 + TS + Vite（按需求确定），周边选型

| 项 | 选择 | 理由 |
|----|------|------|
| 框架 | Vue 3 + TypeScript + Vite | 需求指定 |
| 状态 | Pinia | 连接树、Tab 状态、查询会话跨组件共享 |
| 代码编辑器 | **Monaco Editor** | VS Code 同款，SQL 高亮/补全成熟，可注册 schema 感知的表名/字段名补全；JSON 模式直接复用于 Mongo 查询 |
| UI 组件库 | **Naive UI**（已定，理由见 2.2.1） | TS 支持最好、主题一等公民、按需引入；此类 IDE 型界面大量组件（树/标签页/分割栏）需自绘，组件库只承担表单/弹窗/按钮等基础件 |
| 结果网格 | **ag-grid-community**（免费版） | 虚拟滚动撑 10w+ 行、列宽调整/排序/复制开箱即用；自绘表格扛不住大数据量 |
| 分割布局 | splitpanes | 左右/上下拖拽分栏 |
| 请求 | axios + 原生 WebSocket | 查询执行/AI 流式走 WS，其余走 REST |

#### 2.2.1 组件库与主题方案（已定：Naive UI，暗/亮双主题可切换）

需求：**暗色 + 亮色双主题，自由切换**。三家对比：

| | Naive UI（选定） | Element Plus | Arco Design Vue |
|---|---|---|---|
| 暗色主题 | **内置 `darkTheme`，一行切换，全部组件 token 跟随** | 需额外引入 `dark/css-vars.css`，深浅混排与覆盖成本高一些 | 内置暗色，亦可 |
| TS 体验 | 最好（库本身 TS 编写） | 一般 | 较好 |
| 定制密度 | 主题覆盖走 `themeOverrides` 配置对象，适合深度定制 | SCSS 变量体系，定制偏重 | 中等 |

主题落地方案（双层）：
1. **组件库层**：Naive UI `n-config-provider` 切换 `darkTheme / null`；
2. **自绘层**：连接树、编辑器外框、结果网格、状态栏等 IDE 自绘区域使用**自有 CSS 变量**（`--bg/--panel/--border/--text/...`），由同一个 Pinia theme store 驱动切换 `<html data-theme>`；
3. 联动件：Monaco `vs / vs-dark`、ag-grid `quartz / quartz-dark` 跟随同一 store；
4. 偏好持久化：`settings` 表（服务端）+ `localStorage` 兜底，刷新不丢。

## 3. 核心设计：可插拔驱动层（扩展性的关键）

后续加 Oracle / SQL Server / ClickHouse 时，只新增一个 driver 文件并注册，不动框架。

```python
# drivers/base.py（示意）
class DriverBase(ABC):
    kind: str                      # 'mysql' | 'pg' | ...，注册表用
    editor_mode: str               # 'sql' | 'json-query' | 'command'

    @abstractmethod
    async def connect(self, cfg: ConnConfig) -> None: ...
    @abstractmethod
    async def test(self) -> tuple[bool, str]: ...
    @abstractmethod
    async def metadata_tree(self) -> list[MetaNode]: ...   # 左树
    @abstractmethod
    async def execute(self, session: QuerySession, stmt: str,
                      on_progress: Callable) -> ExecuteResult: ...
    @abstractmethod
    async def cancel(self, query_id: str) -> None: ...

class SqlDriverBase(DriverBase):   # SQL 三家共享骨架
    editor_mode = 'sql'
    # execute 内部统一：多语句拆分 → 逐条执行 → SELECT 返回列头+流式行，
    # DML 返回 affected_rows；统一 LIMIT 注入/分页拉取策略
```

统一结果模型（前端网格只认这一种结构）：

```json
{
  "query_id": "q-8f2a",
  "type": "rows",                      // rows | affected | command | documents
  "columns": [{"name":"id","type":"int"}, {"name":"name","type":"varchar"}],
  "rows": [[1, "张三"], [2, "李四"]],   // 分页拉取，首批返回 N 行
  "has_more": true,
  "affected": null,
  "elapsed_ms": 42
}
```

配套机制：
- **查询会话**：每次执行生成 `query_id`，后台任务执行，WebSocket 推送状态/首批数据；大结果集按 `query_id + cursor` 分页拉取，避免一次把百万行打爆浏览器。
- **查询取消**：`cancel()` 映射到各驱动的取消能力（PG `pg_cancel_backend`、MySQL `KILL QUERY`、SQLite `interrupt`、Redis/Mongo 断连丢弃）。
- **连接池**：按「连接配置」维护长连接池，空闲超时回收；SQLite 特殊（单文件单连接串行）。

## 4. Text-to-SQL 设计

```
用户自然语言 ──► 组装 prompt ──► LLM ──► 流式返回 SQL ──► 插入编辑器 / 执行
                   ▲
        schema 上下文（关键！）
```

- **Schema 上下文**：用户可选中左树的表（推荐方式），或未选时按问题关键词召回相关表；只注入 `CREATE TABLE` 精简 DDL + 少量注释，控制 token（超阈值时截断/只给列名）。
- **方言感知**：prompt 中明确当前是 MySQL 8 / PG 15 / SQLite，方言差异（`LIMIT` vs `TOP`、时间函数）是 text-to-sql 错误大头。
- **安全护栏**：默认只允许生成 `SELECT`（可配置放开写操作）；生成 SQL 先入编辑器由用户确认，不直接执行。
- **Provider 模型（OpenAI 兼容，多配置单生效）**：
  - 只要求 provider 兼容 OpenAI Chat Completions 协议（`POST {base_url}/chat/completions`），DeepSeek / 通义 / 智谱 / OpenAI 官方 / 本地 Ollama 等均可接入；
  - 可配置**多个** provider（名称 + base_url + api_key + model），持久化到 sqlite `ai_providers` 表，api_key Fernet 加密；
  - **任意时刻仅一个生效**（`is_active=1` 全表唯一），在 AI 面板头部下拉即点即切；**不做**按会话/按消息选择不同 provider；
  - 后端统一走 OpenAI 兼容客户端调用，屏蔽厂商 SDK 差异。
- **会话持久化**：AI 面板支持多会话（新建/切换/删除），会话与消息落库 `ai_sessions` / `ai_messages`，刷新/重启后历史可回溯。
- **流式输出**：WebSocket 推送 token，前端打字机效果。

## 5. 应用存储设计（已定：项目内置 SQLite）与安全

应用自身的一切元数据存 **项目内置 SQLite**，不依赖外部数据库：

- 文件位置：`~/.dbshooter/dbshooter.db`（Windows 即 `%USERPROFILE%\.dbshooter\`）；Docker 部署时挂卷持久化。
- 访问层：后端启动时自动建库建表 + 轻量 migration（`PRAGMA user_version` 记录版本号）。
- 敏感字段（连接密码、AI api_key）一律 **Fernet 对称加密**后落库；主密钥来自环境变量 `DBSHOOTER_SECRET`，缺省时首启自动生成 `~/.dbshooter/secret.key`（权限 0600）并提示。

核心表结构（草案）：

```sql
-- 数据库连接
CREATE TABLE connections(
  id TEXT PRIMARY KEY,           -- uuid
  name TEXT NOT NULL,
  type TEXT NOT NULL,            -- sqlite/mysql/pg/redis/mongo
  host TEXT, port INTEGER, database TEXT, username TEXT,
  password_enc TEXT,             -- Fernet 加密
  params_json TEXT,              -- sqlite 文件路径 / redis db 号 / mongo uri / SSL 等扩展项
  readonly INTEGER DEFAULT 0,    -- 只读模式
  sort INTEGER DEFAULT 0,
  created_at TEXT, updated_at TEXT);

-- AI Provider(OpenAI 兼容,多配置单生效)
CREATE TABLE ai_providers(
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,            -- 展示名,如 "DeepSeek"
  base_url TEXT NOT NULL,        -- 如 https://api.deepseek.com/v1
  api_key_enc TEXT,              -- Fernet 加密;本地 ollama 可空
  model TEXT NOT NULL,
  is_active INTEGER DEFAULT 0,   -- 全表仅一行 = 1(切生效时事务内先清后设)
  created_at TEXT, updated_at TEXT);

-- AI 会话与消息(会话需持久化)
CREATE TABLE ai_sessions(
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,           -- 首条问题截断生成
  connection_id TEXT REFERENCES connections(id),
  created_at TEXT, updated_at TEXT);

CREATE TABLE ai_messages(
  id TEXT PRIMARY KEY,
  session_id TEXT NOT NULL REFERENCES ai_sessions(id) ON DELETE CASCADE,
  role TEXT NOT NULL,            -- user | assistant
  content TEXT NOT NULL,         -- assistant 存 JSON: {"text":..., "sql":...}
  tokens INTEGER, elapsed_ms INTEGER,
  created_at TEXT);

-- 查询历史
CREATE TABLE query_history(
  id TEXT PRIMARY KEY, connection_id TEXT, stmt TEXT,
  elapsed_ms INTEGER, row_count INTEGER, status TEXT, executed_at TEXT);

-- 工作区页签(页签与 SQL 内容持久化,重开自动恢复)
CREATE TABLE editor_tabs(
  id TEXT PRIMARY KEY,
  type TEXT NOT NULL,            -- sql | data | redis | mongo
  title TEXT NOT NULL,           -- 如 "SQL-1"、"users 表数据"
  connection_id TEXT REFERENCES connections(id),
  context_json TEXT,             -- 库/schema/表/集合/键 等上下文
  content TEXT,                  -- SQL 或 JSON 查询文本
  sort INTEGER DEFAULT 0,        -- 页签顺序
  is_active INTEGER DEFAULT 0,   -- 关闭前最后活动的页签(恢复时聚焦)
  updated_at TEXT);

-- 通用配置(主题、默认 LIMIT 等)
CREATE TABLE settings(key TEXT PRIMARY KEY, value TEXT);
```

工作区保存策略：编辑器内容**防抖 ~800ms** 自动保存；页签新开/关闭/拖拽排序/切换立即单事务写入；启动时 `GET /api/workspace/tabs` 全量恢复并按 `is_active` 聚焦。

其余安全项：
- 第一期单用户，提供可选全局 access token（环境变量开启）防裸奔；多用户权限体系后置。
- 每个连接可标记 **只读模式**，执行前拦截非 SELECT 语句（与 AI 护栏双保险）。
- AI 生成的 SQL 不直接执行，必须经用户确认。

## 6. API 概览（草案）

> **约束（已定）：接口只用 GET 和 POST**——读操作 GET，写/删/改操作一律 POST（action 风格路径），不使用 PUT/DELETE。

```
GET  /api/connections                    连接列表(密码字段不下发)
POST /api/connections                    新建连接
POST /api/connections/update             更新连接(id 在 body)
POST /api/connections/delete             删除连接(id 在 body)
POST /api/connections/test               测试连接(支持未保存的临时配置)
GET  /api/connections/{id}/metadata      元数据树懒加载 ?path=db.schema.table
GET  /api/connections/{id}/ddl?tables=   text2sql 上下文:表 DDL

POST /api/query/execute                  (备用同步执行;主通道是 WS)
GET  /api/query/{qid}/rows               结果分页 ?offset=&limit=
POST /api/query/cancel                   取消(id 在 body)
GET  /api/query/history                  查询历史

GET  /api/workspace/tabs                 工作区恢复(全部页签 + 内容 + active)
POST /api/workspace/tabs/save            新建/更新页签(内容防抖保存,upsert)
POST /api/workspace/tabs/delete          关闭页签
POST /api/workspace/tabs/order           排序与 active 标记

GET  /api/ai/providers                   Provider 列表(api_key 不下发)
POST /api/ai/providers                   新建
POST /api/ai/providers/update            更新(api_key 留空=不修改)
POST /api/ai/providers/delete            删除
POST /api/ai/providers/activate          设为唯一生效
POST /api/ai/providers/test              连通性测试(GET {base_url}/models)
GET  /api/ai/sessions                    会话列表
POST /api/ai/sessions                    新建会话
POST /api/ai/sessions/delete             删除会话(级联删消息)
POST /api/ai/sessions/rename             重命名
GET  /api/ai/sessions/{id}/messages      消息加载

GET  /api/settings                       通用配置(主题等)
POST /api/settings/save                  保存配置

WebSocket /ws(JSON 消息协议,{id, type, payload} 请求/响应 + 事件推送):
  query.execute   {conn_id, stmt}        → query.started / query.rows / query.done / query.error
  ai.text2sql     {session_id, conn_id, question, tables[]} → ai.token / ai.done / ai.error(消息落库)
```

## 7. 部署与 CI（已定）

### 7.1 Docker 一体化部署（前端由后端托管）

**单镜像交付**：多阶段构建，前端 `vite build` 产物打入后端镜像，由 FastAPI 直接托管静态文件（SPA fallback 到 index.html），对外只暴露一个端口。开发与部署形态：开发时前后端分离（vite dev server 代理 `/api`、`/ws` 到 5718），部署时合一。

```dockerfile
# 阶段一:构建前端
FROM node:20-alpine AS fe
WORKDIR /fe
COPY frontend/package.json frontend/package-lock.json ./
RUN npm ci
COPY frontend/ ./
RUN npm run build

# 阶段二:后端运行时 + 前端产物
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY backend/ ./backend/
COPY run.py .
COPY --from=fe /fe/dist ./frontend_dist/
ENV DBSHOOTER_DATA_DIR=/data
VOLUME /data            # 内置 sqlite、secret.key 持久化
EXPOSE 5718
CMD ["python", "run.py"]
```

```bash
docker build -t dbshooter .
docker run -d -p 5718:5718 -v dbshooter-data:/data \
  -e DBSHOOTER_SECRET=<随机串> dbshooter
```

环境变量：`DBSHOOTER_DATA_DIR`（数据目录，默认 `~/.dbshooter`）、`DBSHOOTER_SECRET`（加密主密钥）、`DBSHOOTER_TOKEN`（可选，访问令牌，设置后 API/WS 需带 `Authorization: Bearer`）。

### 7.2 CI（GitHub Actions）

push / PR 时跑前后端单测，两个独立 job：

- **backend**：setup-python 3.12 → `pip install -r requirements-dev.txt` → `pytest -q`
- **frontend**：setup-node 20 + npm 缓存 → `npm ci` → `npm run test:run`（vitest）→ `npm run build`（构建验证）

## 9. 里程碑

| 里程碑 | 内容 | 验收 |
|--------|------|------|
| M1 骨架 | FastAPI 骨架 + 驱动接口 + SQLite/MySQL/PG 三个驱动；前端布局 + 连接 CRUD + SQL Tab（编辑/执行/结果网格） | 三类 SQL 库跑通「连上 → 浏览表 → 执行 SQL → 看结果」 |
| M2 非关系型 | Redis（命令执行 + key 浏览器）、Mongo（JSON 查询 + 文档视图） | Redis/Mongo Tab 可用 |
| M3 AI | text-to-sql（schema 上下文 + 流式 + 插入编辑器）+ Provider 配置页 | 中文提问生成可执行 SQL |
| M4 打磨 | 结果导出 CSV、查询历史、只读模式、Docker 一体化交付 | 可日常自用 |

## 10. 风险点

1. **大结果集**：必须服务端分页 + 前端虚拟滚动，禁止全量拉取（M1 就做）。
2. **查询取消**各驱动能力不一，SQLite 需 interrupt，Mongo 需 killOp——抽象层要容忍「取消不支持」降级为断连。
3. **Redis key 空间**可能百万级：元数据树用 SCAN 游标 + 按 `:` 分隔懒加载，禁止 `KEYS *`。
4. **AI schema 超 token**：大库必须靠用户选表/相关性召回裁剪上下文。
5. **多语句与事务**：编辑器执行选中语句 vs 全部执行要区分清楚（DBeaver 的 Ctrl+Enter / Alt+X 语义）。
